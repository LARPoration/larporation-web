# ADR-002: Runtime and quality tooling

- Date: 2026-10-03
- Status: Implemented tooling decision

## Decision

Use Node 24.21.0 LTS and its bundled npm 11.19.0. Record the runtime in `.node-version`, declare supported engines, and let CI read the same file. Enable strict engine checks and exact dependency saves.

Move the small existing shell from Next 15.5.27 to stable Next 16.3.8, with matching `@next/eslint-plugin-next`. Use React and React DOM 19.3.0 as a matched pair and TypeScript 5.9.3. The selected package engines and peer ranges were checked against official npm metadata before installation. The shell has no middleware, async request APIs, custom bundler configuration or other migration-sensitive server features.

Use Next 16's default bundler unless validation exposes a concrete incompatibility. Generate route types explicitly before TypeScript checking so a fresh checkout does not depend on an old `.next` directory. Retain any documented TypeScript defaults generated by Next after reviewing them.

Use supported ESLint 10 with core JavaScript rules, TypeScript rules, Next recommended/core-web-vitals rules and React Hooks rules, plus Prettier for formatting. Configure these compatible plugins directly: the full `eslint-config-next` bundle currently pulls React/import/JSX-accessibility plugins whose declared peers exclude ESLint 10. Do not retain that invalid peer tree or adopt EOL ESLint 9. This configuration does not claim the full JSX-accessibility rule set; manual and browser accessibility checks remain necessary. The Prettier compatibility configuration disables conflicting stylistic rules. Run lint explicitly: Next 16 no longer runs it as part of build.

Use Playwright 1.63.0 for production-server browser tests. The initial suite checks existing route/navigation behaviour and 404s; it does not encode the temporary page wording or prototype design. Test servers are started fresh and failures retain diagnostics. The browser suite currently covers Chromium; this does not establish compatibility with every browser.

Pure resource and history contract tests use the Node test runner. No separate component-test framework is configured.

## Consequences

- New contributors must activate the pinned runtime; the old local Node 22 runtime is intentionally rejected for installation.
- CI and local checks share the same scripts and Node pin.
- Dependency upgrades remain separate, reviewable changes with lockfile evidence.
- Prettier reformats the existing shell; JSX apostrophe escaping may change source spelling without changing rendered copy.
- This decision covers runtime and quality tooling, not application architecture or deployment.
- Production hosting must be validated separately against this runtime and the eventual static export.
